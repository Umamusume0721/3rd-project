# 用户与权限数据库设计（C 组）

- 库名：`teamcollab_db`
- 字符集：`utf8mb4`，引擎 `InnoDB`
- 建模方式：RBAC（用户 → 角色 → 权限点），角色与权限都做成表，便于后台配置，不用改代码加角色。

## 一、ER 关系

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_permission >── sys_permission
```

- 一个用户可有多角色（`sys_user_role` 多对多）
- 一个角色可有多权限点（`sys_role_permission` 多对多）
- 权限点粒度到「操作」，含菜单型（MENU）与操作型（ACTION）

## 二、表结构

### 2.1 sys_user 用户表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AI | 用户 ID |
| account | VARCHAR(50) UK | 登录账号，唯一 |
| nickname | VARCHAR(50) | 昵称 / 显示名 |
| email | VARCHAR(100) UK | 邮箱，唯一，可空（MySQL 唯一索引允许多个 NULL） |
| phone | VARCHAR(20) | 手机号，返回时脱敏 |
| password_hash | VARCHAR(100) | **BCrypt 哈希**，禁止存明文 |
| status | TINYINT | 1 启用 / 0 禁用（禁用只拦登录） |
| deleted | TINYINT | 逻辑删除，MyBatis-Plus `@TableLogic` |
| created_at / updated_at | DATETIME | 审计字段，updated_at 自动更新 |

索引：`uk_user_account`、`uk_user_email`、`idx_user_status(status, deleted)`

### 2.2 sys_role 角色表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AI | 角色 ID |
| role_code | VARCHAR(50) UK | 编码，如 `SUPER_ADMIN`，代码里只认编码 |
| role_name | VARCHAR(50) | 显示名 |
| description | VARCHAR(200) | 说明 |
| status | TINYINT | 1 启用 / 0 停用（停用后其权限不生效） |

### 2.3 sys_permission 权限表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AI | 权限 ID |
| code | VARCHAR(80) UK | 权限点，规范 `模块:动作`，如 `task:assign` |
| name | VARCHAR(50) | 名称，给后台配置界面看 |
| type | VARCHAR(20) | `MENU` 菜单 / `ACTION` 操作 |
| parent_id | BIGINT | 父权限，0 为顶级，用于菜单树 |
| sort | INT | 同级排序 |

### 2.4 sys_user_role 用户-角色关联

`user_id` + `role_id`，唯一键 `uk_user_role(user_id, role_id)` 防止重复授权；`idx_ur_role` 支持按角色反查用户。

### 2.5 sys_role_permission 角色-权限关联

`role_id` + `permission_id`，唯一键 `uk_role_permission`；`idx_rp_permission` 支持按权限反查角色。

## 三、关键查询

1. **登录查用户**（`UserMapper.selectByAccount`）
   ```sql
   SELECT ... FROM sys_user WHERE account = #{account} AND deleted = 0 LIMIT 1;
   ```
2. **展开用户权限点**（`PermissionMapper.selectPermCodesByUserId`，三表关联，登录与拦截器共用）
   ```sql
   SELECT DISTINCT p.code
   FROM sys_permission p
   JOIN sys_role_permission rp ON rp.permission_id = p.id
   JOIN sys_user_role ur ON ur.role_id = rp.role_id
   JOIN sys_role r ON r.id = ur.role_id AND r.status = 1
   WHERE ur.user_id = #{userId};
   ```
3. **用户分页 + 角色名称**（`UserMapper.selectUserPage`）
   用 `GROUP_CONCAT(DISTINCT r.role_code ORDER BY r.id SEPARATOR ',')` 把多角色拼成 `TEAM_OWNER,MEMBER`，避免 N+1 次查角色；角色筛选用 `EXISTS` 子查询，不破坏分页。

## 四、初始化数据

- 4 个角色：`SUPER_ADMIN`、`TEAM_OWNER`、`MEMBER`、`GUEST`
- 20 个权限点：用户与权限 7 个（`user:*`、`role:*`）+ 核心业务 14 个（团队、项目、任务、评论）
- 6 个账号，密码统一 `123456`（BCrypt：`$2b$10$J3eBZVVVT...`）

> 超管授权用 `SELECT 1, id FROM sys_permission` 一次授满，后续新增权限点需给超管补授权（或代码层按 `SUPER_ADMIN` 直接放行——本模块采用后者，权限表只是展示用）。

## 五、为什么这样设计（答辩可直接用）

1. **RBAC 而不是写死枚举**：角色、权限都是数据，运营改权限不用发版；新增团队角色只加一行数据。
2. **权限点细到操作**：`user:assign-role`、`task:assign` 这种粒度，前端的按钮显隐与后端的拦截判定用同一套编码，不会出现「前端藏了按钮但接口还能调」。
3. **关联表加唯一键**：授权与去授权是「先删后插」的覆盖式操作，唯一键兜底防止脏数据。
4. **审计字段 + 逻辑删除**：用户数据可追溯，误禁用可恢复；`deleted` 由框架统一处理，业务 SQL 不必到处写。
6. **不做无限分层角色**：4 类角色足够覆盖三阶段项目，层级一多权限判定与测试成本翻倍。
